Field guide · Rust

How to read a Rust codebase

Rust looks alarming at first: ampersands, angle brackets, question marks and exclamation marks everywhere. Most of it decodes into ideas you already use every day as a sysadmin: read-only mounts, file locks, exit codes, pipes and sudo. This guide teaches you to read it, not write it.

The example

TileSmith is JavaScript today, and there's no Rust TileSmith code yet. So this guide reads wallcalc: a small Rust program written for this guide that does one real TileSmith job, working out how many power circuits an LED wall needs, with the same formula as the app. It builds, its 5 tests pass, and its source is in the website folder on GitHub.

Scroll, or use ← → to jump between sections. Code excerpts are the real wallcalc files, with their line numbers.

1 · Different

Why Rust reads differently

JavaScript, like a shell script, runs whatever you give it and fails at the line that's wrong. Rust is compiled: before a Rust program runs at all, the compiler checks every type, every name and every use of memory. Most of the odd symbols exist to give the compiler enough information to do that check.

Sysadmin translation

It's the difference between a shell script and a config that has to pass nginx -t before it loads. Rust code is wordier because it has to pass the check, and once it passes, a whole class of crashes can't happen.

2 · Layout

The layout of a Rust project

A Rust project is called a crate, and every crate has the same shape. Learn it once and you can open any Rust repository on GitHub and know where to look.

wallcalc/
├── Cargo.toml      # name, version, dependencies
├── Cargo.lock      # exact versions used (generated)
├── src/
│   ├── main.rs     # the program starts here
│   ├── lib.rs      # the library: lists the modules
│   ├── tile.rs     # one module per file
│   ├── power.rs
│   ├── error.rs
│   ├── output.rs
│   └── ffi.rs
└── target/         # build output: ignore it
Sysadmin translation

Cargo.toml is the package manifest, like a .spec file or a debian/control. Cargo.lock pins the exact versions, like a lock file from pip freeze. wallcalc has no dependencies, so its [dependencies] list is empty.

Bigger projects

A workspace is several crates in one repository. Its top Cargo.toml has a [workspace] section listing them under members. Read that list first: it's the table of contents.

Other folders

tests/ holds tests that use the crate from outside. examples/ holds small programs you can run with cargo run --example name. benches/ holds speed tests.

build.rs

If a crate has a build.rs next to Cargo.toml, it's a script that runs before the build, often to find a C library. Worth a look when a build fails.

3 · Start here

Where to start: fn main

A program starts at fn main() in src/main.rs. Read it top to bottom like an init script. In a well-organised crate, main is short: it reads the command line, builds the objects, calls the library and turns the result into an exit code.

Sysadmin translation

ExitCode::from(2) is exit 2. eprintln! writes to stderr and println! to stdout. This program behaves like any good CLI tool: usage errors exit 2, failures exit 1, success exits 0.

  1. Lines 1 and 2 start with //!: documentation for the whole file. Comments starting /// document the item below them. Plain // is an ordinary comment.
  2. Lines 4 to 8, use, are imports: they let the file write Circuit instead of wallcalc::power::Circuit. std:: is Rust's standard library.
  3. Line 10: fn main() -> ExitCode is a function called main that takes nothing and gives back an exit code. -> always means "returns".
  4. Line 11 collects the command-line arguments into a list of strings, Vec<String>. Read Vec<String> as "list of String".
  5. Line 17 parses both numbers, and match picks a branch: if both are Ok, keep them; if either is an Err, print it and exit 2.
  6. Line 34 asks the wall how many circuits it needs. The answer is either Ok(n) or an Err(e), and the program must handle both. More in part 9.
4 · Modules

How files find each other

Rust doesn't load every file in src/. A file is part of the program only if something names it with mod. So lib.rs is the library's table of contents.

  1. pub mod power; means "the module power is in src/power.rs" (or in src/power/mod.rs in older code). pub makes it visible outside the crate.
  2. Inside the crate, files refer to each other from the top with crate::, like an absolute path from /:
  3. :: is the path separator, like / in a file path. {Tile, Wall} imports two names at once, like {a,b} in a shell.
  4. Anything without pub is private to its file. parse_count in main.rs has no pub, so nothing else can call it.
Sysadmin translation

mod is an include line in a config. pub is the file permission: without it, other modules get "permission denied" at build time.

6 · Types

Structs, enums and match

Rust code is organised around its types, so read the types before the functions. A struct is a record with named fields. An enum is a value that's exactly one of a fixed list of options. match handles each option.

Sysadmin translation

A struct is a row in a CSV with fixed columns. An enum is a setting that only accepts certain words, like PermitRootLogin yes|no|prohibit-password, except the compiler enforces it everywhere.

  1. Line 4: #[derive(…)] asks the compiler to generate standard abilities: print for debugging, copy, compare with ==.
  2. Lines 32 to 35: a BuildMode is either GroundStack or Flown, nothing else. No typos, no "unknown mode" at show time.
  3. Lines 58 to 61: match must cover every option. Add a third build mode to the enum and this function stops building until someone decides which row it starts on. That's the compiler doing a code review for you.
7 · impl

impl and traits

Functions that belong to a type live in an impl block. A trait is a named set of abilities, and impl Trait for Type gives a type that ability. You'll see impl Default for …, impl Display for … and impl From<…> for … in almost every crate.

Sysadmin translation

A trait is an interface contract, like "anything that speaks SNMP". impl Display for PowerError says "PowerError can be printed as text", so println!("{e}") works on it.

  1. Circuit::default() in main.rs calls the first block: 120 V, 20 A, loaded to 80%, power factor 1. The same defaults as TileSmith.
  2. usable_watts is the formula from TileSmith's spec. if … { 0.8 } else { 1.0 } is an expression that gives a value, like $(…) in a shell.
  3. Methods can be spread across files. Wall is defined in tile.rs, but its circuits_needed method is in an impl Wall block in power.rs. Search for fn circuits_needed, not for the struct, or use your editor's "go to definition" (part 13).
8 · Ownership

Ownership and borrowing

This is the one genuinely new idea. Every value has exactly one owner. When the owner goes away, the value is freed. You can move a value to a new owner, or lend it: many read-only loans (&) or one exclusive, writable loan (&mut), never both at once.

Sysadmin translation

A move is handing over a physical drive: you don't have it any more. & is a read-only NFS export: many clients, nobody writes. &mut is an exclusive flock: one writer and no readers. Rust checks those rules when it builds, so two parts of the program can't both change the same thing at once.

let a = String::from("Main wall");
a"Main wall"
b
c

a owns the text. When a goes out of scope (at the closing }), the text is freed. No garbage collector needed.

let b = a;            // the text moves to b
println!("{a}");     // build error: a has given it away
a (moved)
b"Main wall"
c

Assigning moves the value: there's still only one copy, and now b owns it. Using a again is a build error, "borrow of moved value".

let c = &b;           // lend it, read-only
println!("{b} {c}");  // fine: both can read
a (moved)
b"Main wall"
c&b (read-only)

&b lends without moving. That's why wallcalc's functions take c: &Circuit and tile: &Tile: they read the circuit and the tile, then give them back untouched.

let mut b = String::from("Main wall");
let w = &mut b;       // exclusive loan
w.push_str(" (flown)");
// while w is in use, nobody else can read or write b
a (moved)
b (lent out)"Main wall (flown)"
w&mut b (writer)

&mut is the exclusive lock. When you see &mut in a function's arguments, that function changes what it's given. Everything else is read-only. That alone tells you a lot about what a function does.

let d = b.clone();    // a real second copy
b"Main wall (flown)"
d"Main wall (flown)"
c

.clone() makes an independent copy, which costs memory and time, so Rust makes you ask for it. wallcalc's tile.name.clone() copies a tile's name into an error message. When you see many .clone() calls, someone was working around the borrow rules.

9 · Errors

Result, Option and ?

Rust has no exceptions and no null. A function that can fail returns a Result: Ok(value) or Err(problem). A value that might be missing is an Option: Some(value) or None. The caller has to unpack them, so you can always see where failures are handled.

Sysadmin translation

Result is an exit code you're not allowed to ignore. ? is || return $?: pass the failure up to the caller. .unwrap() and .expect("…") mean "this can't fail, and if it does, crash": like a script with no error handling.

  1. parse_count returns Result<u32, String>: a number, or a message saying what was wrong.
  2. Line 56: .map_err(…) swaps Rust's own parse error for a friendlier message, and ? returns early with it if the text wasn't a number.
  3. error.rs lists every way power planning can fail, as an enum. Reading the error enum is a fast way to learn what can go wrong in a module.
# where can this program crash on purpose? (from the crate folder)
grep -rn -E '\.unwrap\(\)|\.expect\(|panic!' src
10 · Threads

Threads, pipes and locks

A video output like NDI® should run on its own thread so a slow network never stalls the drawing. wallcalc's output.rs shows the pattern: a worker thread reads frames from a channel, and both threads share a counter behind a lock.

Sysadmin translation

A channel is a pipe: tx is the write end, rx the read end, and the reader's loop ends when every writer closes. Mutex is a lock file around shared data. Arc is a reference count, like hard links: the data is freed when the last link goes.

  1. Line 15: Arc::new(Mutex::new(0u64)) is a counter wrapped in a lock, wrapped in a shareable handle.
  2. Line 19: thread::spawn(move || { … }) starts a thread running the closure. move hands it ownership of what it uses (the read end and its own handle to the counter).
  3. Line 23: .lock().unwrap() takes the lock, and the lock is released by itself at the end of the statement. You can't touch the counter without the lock: the compiler won't allow it.
  4. Lines 35 and 36: drop(tx) closes the pipe, and join() waits for the worker to finish, like wait in a shell.
11 · unsafe

unsafe: Rust's sudo

Some things the compiler can't check: calling a C library, or working with raw memory addresses. That code goes inside unsafe, which means "trust me, I checked this by hand". TileSmith calls the NDI® library from JavaScript today, and a Rust version would do it like this.

Sysadmin translation

unsafe is sudo. It doesn't make code dangerous, it marks where the safety checks are switched off. When reviewing a Rust project, grep -rn unsafe shows you every line that deserves a closer look.

  1. Line 7: #[repr(C)] lays the struct out exactly as C would, so the NDI® library reads the right bytes.
  2. Lines 9 and 10: *const c_char is a raw pointer to C text. Raw pointers are the one thing safe Rust never dereferences.
  3. Lines 15 to 18: unsafe extern "C" declares functions that live in a C library. Every call to them must itself sit inside an unsafe { … } block. wallcalc only declares them and never calls them, so it doesn't need NDI® installed.
12 · Tests

Tests live next to the code

Rust tests usually sit at the bottom of the file they test, in a block marked #[cfg(test)], which is only built when testing. Each test is a function marked #[test]. They're the quickest way to see how a function is meant to be called and what it should return.

Sysadmin translation

assert_eq!(a, b) is [ "$a" = "$b" ] || exit 1. cargo test runs every test in parallel and prints one line per test.

$ cargo test
running 5 tests
test power::tests::a_tile_bigger_than_a_circuit_is_an_error ... ok
test power::tests::a_wall_rounds_circuits_up ... ok
test power::tests::link_limit_caps_the_count ... ok
test power::tests::matches_the_spec_example ... ok
test output::tests::every_frame_is_handled ... ok

test result: ok. 5 passed; 0 failed

use super::*; pulls in everything from the file above the test block. The first test checks the same worked example as TileSmith's spec: 120 V × 20 A × 0.8 = 1,920 W, which fits 16 tiles of 120 W.

14 · Quiz

Will it compile?

Guess before you click. Every answer was checked with the real compiler.

let total = 0;
total += 1;

Build error: "cannot assign twice to immutable variable". Variables can't change unless they're declared let mut total. So when you read Rust, mut marks every place state can change.

let a = String::from("Main wall");
let b = a;
println!("{a}");

Build error: "borrow of moved value: a". The text moved to b (part 8). let b = &a; or let b = a.clone(); would both work.

let t = Tile::new("Demo 500", 192, 192, 120.0, 6.3);
let a = t.pixels();
let b = t.pixels();

Compiles. pixels(&self) only borrows the tile to read it, so you can call it as often as you like. Only a method taking self without the & would use the tile up.

fn first_row(mode: BuildMode) -> &'static str {
    match mode {
        BuildMode::GroundStack => "bottom",
    }
}

Build error: "non-exhaustive patterns: BuildMode::Flown not covered". match must handle every option of the enum (part 6). A shell case would just fall through and do nothing.

fn main() {
    let n: u32 = "12".parse()?;
}

Build error: "the ? operator can only be used in a function that returns Result or Option". ? passes an error up to the caller, so the function needs a way to return one. wallcalc's main returns an ExitCode and handles errors with match instead.

15 · Looking ahead

If TileSmith moves to Rust

A Rust rewrite has been considered, and none of it exists yet. If it happens, it will be laid out differently from today's single file, but the ideas will carry over. Here's where to look for the things you know from the tour and the JavaScript guide. This is a likely shape, not a plan.

How to read it on day one

Open the top Cargo.toml and read the workspace members and dependencies. Then src/main.rs, then lib.rs for the module list. Then the types in the settings module. You'll know the shape of the whole app in half an hour.

Break it yourself

The best Rust teacher is the compiler. Its error messages say what's wrong, point at the line, and usually suggest the fix.

# install Rust (Windows: download rustup-init.exe from rustup.rs)
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh

# get wallcalc and run it
git clone https://github.com/kingof9x/TileSmith
cd TileSmith/website/read-rust/wallcalc
cargo run -- 10 5
cargo test
Three things to break

1. In tile.rs, add a third build mode, Truss, and read what the compiler says about first_row.
2. In power.rs, change 0.8 to 0.9 and run cargo test: watch the spec test fail.
3. In main.rs, remove a & from &circuit and read the error. Then put everything back with git checkout .
