Before we start

How to read the code on these slides

TileSmith is written in JavaScript. If you've written bash or PowerShell, you already know most of the ideas. The syntax is just different.

The real file is written very densely, with short names like S, M and w and many statements on one line. On these slides the code is spread out over more lines and lightly trimmed (a // … marks a cut). The names and logic are the real ones.

Part 1 · Startup

What happens when you open the app

What it does

The window opens, your last project reappears exactly as you left it, the panels fill in, and the wall starts drawing. If you'd left the LED build running, it starts again.

Sysadmin translation

This is the app's init script. It runs once, top to bottom, at the very end of the file, after every function has been defined.

How the code works
// last lines of index.html (spread out)
const DESK = typeof require == 'function' && !!process.versions.electron;  // line 5599: are we inside Electron?
// …
CVS = [cvFromGlobals('Canvas 1')]; cc = 0;   // one canvas to start with
loadState();               // read state.json into S and walls
build();                   // write the left panel's HTML
outInit();                 // ask Electron which displays are plugged in
showAll();                 // every wall starts fully built
M.width = S.cw; M.height = S.ch;   // size the hidden master canvas
fit();                     // zoom so the canvas fits the window
unBase();                  // first undo snapshot
requestAnimationFrame(loop);       // start the drawing loop
if (bldRun) { eachCv(() => reset()); S.play = true }  // resume the LED build
  1. DESK checks whether Node.js's require exists and Electron's version is set. The same page runs in a browser, on a phone and on the desktop, so dozens of features ask if (DESK) before touching files or drivers. A second flag, MOBILE, checks for Capacitor, the phone wrapper.
  2. loadState() reads the saved settings (part 4). It runs before the panels are built so they show your values, not the defaults.
  3. build() generates the HTML for the left panel from text templates (part 3).
  4. requestAnimationFrame(loop) asks the browser to call loop before the next screen refresh. loop asks again every time, so it runs forever (part 7).
Part 2 · Settings

Everything lives in one object, S

What it does

Every setting you can touch, about 200 of them (canvas size, tile model, border colour, which processor, NDI® name, label size…), has one home. Each wall also remembers its own settings, so two walls can have different tiles and patterns.

Sysadmin translation

S is the running config. The wall list is like per-host overrides in Ansible: some keys belong to the whole app, some to one wall.

How the code works
// line 2690: the defaults, one key per line
const S = {
  cw: 1920,
  ch: 1080,
  ox: 0, oy: 0,        // wall position
  cols: 6, rows: 4,
  preset: 'Unilumin UpadIV 2.6',
  tw: 192,            // tile width in px
  // … about 200 keys
};
// line 2924: which keys belong to a wall
const WK = ['half', 'gone', 'lay', /* … */];
// the selected wall's keys are copied in and out
function storeWall() {
  if (walls[cur])
    WK.forEach(k => walls[cur][k] = S[k]);
}
function loadWall(i) {
  cur = i;
  WK.forEach(k => S[k] = walls[cur][k]);
}
function selWall(i) {   // you clicked a wall
  storeWall();   // save the old one
  loadWall(i);   // bring in the new one
  sync();        // refresh the panels
}
  1. S holds the settings the panels show. walls is a list of objects, one per LED wall, and cur is the number of the selected wall.
  2. The panels only ever edit S. When you pick another wall, storeWall copies the wall keys (WK) from S back into the old wall, and loadWall copies the new wall's keys into S. That's why the same "Tile model" box edits whichever wall is selected.
  3. A second list, LIM (line 3357), gives each number its allowed range, for example lblCopies: [1, 4]. Every value typed in or loaded from a file is clamped to it.
  4. The comment "one key per line" is deliberate: when two changes are made at once, they add different lines, so git can merge them without a conflict.
Part 3 · The settings panels

Panels built from text templates

What it does

The left column has collapsible sections (Canvases, LED walls, Test pattern, Engineering…). Change any box and the wall, the engineering numbers and every output update straight away.

Sysadmin translation

Instead of wiring up 200 boxes one by one, every input is tagged with the name of the setting it edits, and one event handler serves them all. Like one generic script that reads key=value lines rather than one script per setting.

How the code works
// line 3120: F() writes the HTML for one box (simplified)
const F = (k, label, type = 'number') =>

   </label>`;

// line 3426 (trimmed)

function applyKey(t) {
  const k = t.dataset.k;       // which setting?
  let v = t.type == 'checkbox' ? t.checked : +t.value;
  const L = LIM[k];
  if (L) v = Math.max(L[0], Math.min(L[1], v)); // clamp
  S[k] = v;                     // store it
  if (k == 'preset') applyPreset();  // side effects
  if (['proc','fps','bpc'].includes(k)) applySpec();
  storeWall();
}
  1. Template strings (text in backticks with ${…} holes) build the HTML as one long string. sect() turns every <h2> into a collapsible <details> section.
  2. Every input carries data-k="cw", the name of its key in S. applyKey reads that tag, converts the value (number, tick box or text), clamps it with LIM and stores it.
  3. A few keys have knock-on effects. Picking a tile model (preset) copies that tile's size, weight and watts into the wall. Changing the processor or frame rate recalculates pixels per port.
  4. sync() (line 3251) then walks the other way: it pushes S back into every box, shows or hides sections, and rebuilds the engineering table. It's a list with one call per line, one per feature.
Part 4 · Saving, projects and undo

Save 400 ms after you stop

What it does

There's no Save button for everyday use. Settings are written to disk by themselves. You can also save and open whole .tilesmith project files, and undo or redo the last 20 changes with Ctrl+Z.

Sysadmin translation

The 400 ms wait is a debounce: like a log shipper that batches lines instead of making a network call per line. Drag a slider and you get one write at the end, not 60 a second.

How the code works
// line 6210: restart a 400 ms timer on every change
function saveSoon() {
  clearTimeout(saveT);
  saveT = setTimeout(saveNow, 400);
}
['input','change','click','pointerup']

  } else localStorage.setItem(SKEY, j);
  // if that fails (disk full, browser quota):
  // drop the uploaded images and try again
}

  const k = unKey(sn);          // …as one JSON string

// loading checks every value (line 6275)

  1. stFile() picks the folder: %APPDATA%\TileSmith on Windows, ~/Library/Application Support/TileSmith on a Mac, $XDG_CONFIG_HOME/TileSmith (or ~/.config) on Linux. The browser version uses localStorage instead.
  2. stateObj() gathers S, every wall on every canvas, the crew and uploaded logos (as data: text) into one object, tagged sv: 24, the save-format version. A Save Project file is the same JSON with a header added.
  3. Loading never trusts the file. It only takes keys the app knows, only if the type matches (a number stays a number), and clamps numbers to LIM. Old formats are upgraded: patterns renamed in v2.7 are mapped to their new names, and half tiles from older versions are converted.
  4. Undo keeps whole snapshots, not individual edits. After every click or keystroke it takes a new snapshot, turns it into one JSON string, and compares that with the last one. If they differ, the old snapshot goes on the undo stack. Simple and hard to get wrong, at the cost of some memory.
  5. The app also saves on beforeunload, pagehide and when the window is hidden, so closing it never loses the last 400 ms.
Part 5 · Walls and tiles

A wall is a list of pieces

What it does

You pick a tile model from a catalog of about 400 real products (ROE, Absen, INFiLED, Unilumin…), set columns and rows, and can remove tiles or use half tiles to make stepped or offset walls. Each tile gets an ID, a pixel address and a build order.

Sysadmin translation

pieces() is like generating an inventory from a template: give it the rack layout and it hands back a list of every unit with its position, size, weight and power. And it caches the result until the layout changes.

How the code works
// the catalog: one line per model
// [mm wide, mm high, px wide, px high,
//  pitch, kg, max watts, depth]
const P = {
  'ROE Black Pearl BP2V2':
     [500,500, 176,176, 2.84, 9.35, 190, 90],
  // … about 400 more
};
// line 3075 (plain grid, trimmed)
function pieces(w) {
  const key = [w.cols, w.rows, w.tw, w.th, /*…*/].join('|');
  let e = PCQ.get(w);
  if (e && e.k === key) return e.v;  // cached
  const gs = goneSet(w), list = [];    // removed tiles
  for (let r = 0; r < w.rows; r++)
    for (let c = 0; c < w.cols; c++) {
      if (gs.has(r * w.cols + c)) continue;
      list.push({ key: c + ',' + r, c, r,
        x: c * w.tw, y: r * w.th, w: w.tw, h: w.th,
        o: ord.get(r * w.cols + c),       // build order
        sp: {kg: w.kg, W: w.wmax} });
    }
  const seq = [...list].sort((p, q) => p.o - q.o);
  PCQ.set(w, {k: key, v: {list, seq, /*…*/}});
}
  1. Each piece is one physical tile: its column and row, its place in wall pixels (x, y, w, h), its weight and watts (sp) and its place in the build order (o). Rendering, wiring, power, labels and the animation all read this one list.
  2. Caching: working out a 40 × 20 wall every frame would be wasteful. The function makes a text key from everything that affects the layout. If the key matches last time, it returns the stored answer. PCQ is a WeakMap, a cache that forgets a wall's entry when the wall is deleted.
  3. Build order comes from seqRC(w, k): "the k-th tile placed is at column c, row r", given the start corner, row-by-row or column-by-column, and ground stack or flown (flown walls always hang the top row first).
  4. Half tiles use a finer grid where each cell is half a tile. A full tile takes two cells, upright or (for some ROE models) on its side, so walls can step by half a tile. The same pieces() handles both and hands back the same kind of list.
Part 6 · The viewport

One pointer, many modes

What it does

The centre of the window shows the canvas. Drag empty space to pan, scroll or pinch to zoom, drag a wall to move it (it snaps to edges and other walls), or click tiles to wire them, remove them, mark half tiles or pick faulty ones.

Sysadmin translation

A small state machine: press decides the mode (pan, move wall, wire…), move does that mode's job, release ends it. Like a CLI that picks a subcommand from the first word.

How the code works
// line 3530: pointer pressed on the viewport
vp.onpointerdown = e => {
  const i = hitWall(e);          // which wall is under it?
  drag = {mode: 'pan', /* start position */};
  if (glEdit   && i == cur) { drag.mode = 'glk';  return }
  if (goneEdit && i == cur) { drag.mode = 'gone'; return }
  if (halfEdit && i == cur) { drag.mode = 'half'; return }
  if (manWiring() && i == cur) { drag.mode = 'wire'; return }
  if (i >= 0) { selWall(i); drag.mode = 'wall' }
};
vp.onpointermove = e => {
  if (drag.mode == 'wall') {
    let [x, y] = /* start + how far you moved */;
    if (!e.altKey) [x, y] = snapPos(cur, x, y);
    S.ox = x; S.oy = y; sync();
  }
  // … pan, wire, half, gone
};
// screen pixels → canvas pixels
// V = {x, y, z}: pan offset and zoom
toCv(e) = [(e.x - V.x) / V.z,
           (e.y - V.y) / V.z]

// line 3495: last wall drawn wins
function hitWall(e) {
  const [x, y] = toCv(e);
  for (let i = walls.length - 1; i >= 0; i--) {
    const w = walls[i];
    if (x >= w.ox && y >= w.oy &&
        x < w.ox + wW(w) && y < w.oy + wH(w))
      return i;
  }
  return -1;
}
  1. toCv converts a mouse position on screen into canvas pixels by undoing the pan (V.x, V.y) and zoom (V.z). Everything after that works in real canvas pixels, whatever the zoom.
  2. hitWall checks walls from last to first, because later walls are drawn on top. The first rectangle that contains the point wins.
  3. snapPos compares the wall's edges with the canvas edges and every other wall's edges. Anything within 10 screen pixels snaps, including "beside it with a 2 px gap". Magenta guide lines show what it snapped to. Holding Alt skips snapping.
  4. Two fingers on a touch screen go through a separate pinch handler that zooms around the point between your fingers.
Part 7 · The main loop

Redraw only when something changed

What it does

The picture moves smoothly at up to 60 frames a second while something is animating, and goes almost idle when nothing is. A still wall costs almost no CPU, so a laptop stays cool during a long show.

Sysadmin translation

A scheduler with a dirty flag. It wakes every screen refresh, but only does the expensive work (a full redraw) when something is marked as changed, plus a 4-per-second health check.

How the code works
// line 6199: runs on every screen refresh
function loop() {
  requestAnimationFrame(loop);      // book the next call
  const now = performance.now();
  // cap at 60 per second (on a 144 Hz screen too)
  if (now >= nextT - F * .25) { tick(now); nextT += F }
  // copy the master canvas to the screen
  if (RG !== vpGen) { vpDraw(); vpGen = RG }
}

function tick(now) {
  const dt = (now - lastStep) / 1000;  // seconds since last
  const per = now - lastRen >= 250;   // 4× a second anyway
  eachCv(() => {                       // every canvas
    step(dt);                          // move the crew
    dvdStep(dt);                       // move the DVD logo
    if (forceRen || per || busyNow(now)) {
      render(); gen++;                 // draw a new frame
    }
  });
}
// line 6189: is anything moving?
function animNow() {
  if (S.dvdOn || REC || S.play && !allDone())
    return true;
  if (sims.some(x => x.sp.length))   // sparkles
    return true;
  return walls.some(w =>
    MOVE_PAT.includes(w.pat) || scrolls(w));
}
function busyNow(now) {
  return !!drag                // you're dragging
    || now - lastAct < 1200    // you touched it
    || animNow();
}
  1. requestAnimationFrame is the browser's "call me before the next screen refresh". Calling it again at the top of loop keeps it going forever.
  2. tick does the work: it moves every animation forward by dt seconds (so speed is the same at 30 or 60 fps), then decides whether to redraw.
  3. It redraws if something forced it (forceRen, set when a setting or image changes), if 250 ms have passed, if you touched the app in the last 1.2 s, or if animNow() finds anything moving.
  4. Every redraw bumps a counter, gen. Outputs remember the last gen they sent, so a still picture is never read or sent twice (part 15).
  5. While NDI® or Spout is running, a separate output timer calls tick instead, at exactly the output's frame rate, even when the window is hidden (browsers slow down hidden tabs; main.js turns that off).
Part 8 · Drawing a frame

Paint it back to front

What it does

Each frame shows every wall: its pattern on built tiles, dashed outlines where tiles are still missing, borders, tile IDs, pixel addresses, position arrows, data and power runs, then the technicians and the lock sparkles on top.

Sysadmin translation

Like regenerating a report from scratch on every run instead of patching yesterday's. No pixel is kept from the last frame, so nothing can get stuck on screen.

How the code works
// line 4304 (heavily trimmed)
function render() {
  const c = mc;                    // M's drawing context
  c.fillStyle = '#050608';
  c.fillRect(0, 0, S.cw, S.ch);       // 1. wipe
  walls.forEach((w, wi) => {
    const PW = pieces(w), sm = sims[wi];
    // which tiles are built so far?
    for (let k = 0; k < sm.inst; k++) inst.add(PW.seq[k].key);
    // 2. dashed outline on unbuilt tiles
    // 3. pattern, clipped to built tiles
    c.save(); litClip(); c.translate(w.ox, w.oy);
    pat(c, w, wW(w), wH(w)); dvdDraw(c, w);
    c.restore();
    // 4. per tile: border, corner marks, labels
    PW.list.forEach(R => { /* strokeRect, fillText */ });
    // 5. data paths: coloured lines + P#/R# badges
    // 6. power runs: dashed lines + ⚡ circuit badges
  });
  busy.forEach(wi => drawWallTech(c, walls[wi], sims[wi]));
  // 7. lock sparkles: expanding rings
}

Untick a layer to take it out of the frame. The numbers match the steps in the code.

  1. A canvas is a grid of pixels you draw on with commands like fillRect (filled box), strokeRect (outline), fillText and drawImage. mc is the drawing handle for the hidden master canvas M.
  2. Clipping is how half-built walls work. litClip() marks out only the built tiles; while the clip is on, drawing outside it is thrown away. So the pattern is drawn for the whole wall, but only shows on tiles that are in place.
  3. translate moves the drawing origin to the wall's corner, so the pattern code can always draw from (0, 0) without knowing where the wall sits on the canvas. save() and restore() undo the clip and the move afterwards.
  4. Label sizes scale with the tile (fs = max(8, min(tw/9, th/7))), so a 128 px tile and a 512 px tile both get readable text.
  5. The screen never sees M directly. vpDraw() copies it into the visible viewport at your zoom with one drawImage, then draws the editing aids (amber wall outlines, snap guides) on top. Those aids never reach the LED wall.
Part 9 · Test patterns

Most patterns are arithmetic

What it does

About 25 patterns: the tileshade pixel map, SMPTE bars, ramps, gradients, a zone plate, colour cycles, cabinet IDs, disguise and branded test cards, or your own image. Any of them can scroll.

Sysadmin translation

pat() is a dispatcher, like a case statement that hands each pattern to its own handler. Pictures are cached, maths is just run again.

How the code works
// line 3624: pick the right drawer
function pat(c, L, w, h) {
  if (L.pat == 'cabinet IDs') return cidPat(c, L, w, h);
  if (isImgPat(L.pat))       return drawImgPat(c, L, w, h);
  if (!scrolls(L))           return patRaw(c, L, w, h);
  // scrolling: draw once into an offscreen canvas,
  // then stamp it 4 times, shifted, so it wraps
  blitWrap(c, e.cv, w, h, scrollOff(L, w, h));
}
// line 3629: the maths patterns
function patRaw(c, L, w, h) {
  if (p == 'ramp')            // 16 grey steps
    for (let i = 0; i < 16; i++) {
      const g = Math.round(i * 255 / 15);
      c.fillStyle = `rgb(${g},${g},${g})`;
      c.fillRect(i * w / 16, 0, w / 16 + 1, h);
    }
  else if (p == 'cycle')        // new colour every 1.5 s
    c.fillStyle = ['#f00','#0f0','#00f',/*…*/]
                  [Math.floor(T / 1.5) % 8];
  else if (isShade(p))            // tileshade family
    for (r…) for (q…)
      c.fillStyle = (q + r) % 2 ? mixW(L.shadeC, .5) : L.shadeC;
  // …
}

tileshade-cycle, live: tile colour = [red, green, blue][(col + 2×row + k) mod 3], where k goes up every 2.5 s. One step right adds 1, one step down adds 2. Neither is a multiple of 3, so neighbours never match. The number on each tile is that sum mod 3.

  1. T is the time in seconds, set once per frame. Every moving pattern is a formula of T, which is also what lets video export run frame by frame faster or slower than real time and still look right.
  2. The checkerboard: (q + r) % 2 is 0 or 1 alternately across columns q and rows r. Even tiles get your colour, odd ones get it mixed 50% with white.
  3. Images (SMPTE, disguise cards, your upload) are drawn with drawImage using one of five fit modes. Very large walls render the cached image at a reduced scale so it stays under 25 megapixels.
  4. Scrolling: drawing a complex pattern 60 times a second is slow, so it's drawn once into a spare offscreen canvas. Each frame stamps that canvas four times, shifted by the scroll offset, so whatever slides off one edge reappears on the other.
Part 10 · Processors and data wiring

Fill each port, snake the cable

What it does

Pick an LED processor (Brompton, NovaStar, Megapixel, ROE) and the app works out how many tiles each port can drive at your frame rate and bit depth, then plans the cable runs in one of 16 patterns (start corner × direction × snake or linear), or lets you draw them by hand.

Sysadmin translation

Bandwidth planning. Each port is a 1 Gb uplink with a pixel budget. Higher frame rate or bit depth means fewer pixels fit, exactly like higher bitrate means fewer streams per link.

How the code works
// line 3763: pixels per port for your settings
function specPx(m) {
  let v = m.px * m.hz / S.fps;     // scale by frame rate
  if (m.sc == 'brompton') {
    v *= 8 / S.bpc;                  // scale by bit depth
    if (S.ull) v /= 2;               // ultra low latency
  } else if (m.sc == 'novastar') {
    if (S.bpc > 8) v = m.px10 ? m.px10 * m.hz / S.fps : v / 2;
  }
  return Math.floor(v);
}
// tiles per port
const tpp = w => Math.floor(S.ppx / (w.tw * w.th));

// line 3812: lay a cable through a block
function blockPath(len, nl, snake) {
  const o = [];
  for (let l = 0; l < nl; l++)          // each line
    for (let k = 0; k < len; k++)       // along it
      o.push([snake && l % 2 ? len - 1 - k : k, l]);
  return o;
}

Try it

  1. PROC is a table of about 30 processors with ports, pixels per port, the frame rate and bit depth that figure is quoted at, and a scaling rule (sc). Each brand scales differently, so specPx has one branch per rule.
  2. blockPath produces the order tiles are visited in one block: line by line, and with snake on, every second line runs backwards (the len - 1 - k). That's the zig-zag you see on the wall.

Part 14 · The DVD screensaver

Yes, it hits the corner

What it does

A logo bounces around each wall, changing colour on each bounce. A slider sets how often it lands exactly in a corner, and "perfect loop" makes a video that loops without a seam.

How the code works
// line 6116: after every bounce, roll the dice
function dvdDecide(st) {
  if (S.dvdCorner > 0 && Math.random() * 100 < S.dvdCorner * DVD_MAX)
    dvdAim(st);                 // hit: steer into a corner
  else { st.mode = 'free'; dvdAvoid(st) }   // miss: make sure it misses
}
// dvdAim: list candidate corners, reached directly or after one more bounce
//   distance to a corner = (gap to the near wall) + (k - 1) × (wall size)
//   angle = atan2(distance Y, distance X); keep 2° … 88°
//   score = fewest bounces, then keep direction, then the smallest turn
// dvdAvoid: if the next hit lands too close to a corner, turn up to 60° until it doesn't
  1. DVD_MAX = 0.45: at 100% about 45% of bounces aim for a corner. Higher would look rigged.
  2. Aiming uses the mirror trick: a bounce off a wall is the same as carrying straight on into a mirrored copy of the wall. So "reach the corner after one bounce" becomes "reach the corner of the next mirrored copy", a straight line whose angle is one atan2.
  3. Avoiding matters just as much: at 0% the logo must never hit a corner by luck. dvdMiss works out where the next hit lands; if it's within a margin of a corner, dvdAvoid tries angles one degree at a time either side until it misses.
  4. Perfect loop picks two whole numbers m and n with no common factor. In T seconds the logo crosses the width 2m times and the height 2n times, so it's back at the start, going the same way. Colours come from a seeded list, so they repeat too.

function recFrame(r) {
  const w = r.pr.stdin;
  const due = Math.floor((performance.now() - r.t0) * .06) + 1;  // frames owed so far
  if (r.written >= due || w.writableLength > 256e6) return;      // up to date, or ffmpeg is behind
  const buf = Buffer.from(grabFrame().data.buffer);
  while (r.written < due) { w.write(buf); r.written++ }          // repeat to catch up
}
  1. spawn starts ffmpeg like typing the command in a terminal, but with its standard input connected to TileSmith. windowsHide stops a console window flashing up on Windows.
  2. Timing: 0.06 frames per millisecond is 60 fps. If the app fell behind (a slow frame), it writes the same picture again until the count catches up, so the video's length always matches real time.
  3. Back-pressure: if more than 256 MB is waiting in the pipe (ffmpeg can't keep up), it skips writing for now instead of filling the computer's memory. A sysadmin would recognise this as a bounded queue.
  4. When ffmpeg exits, a code of 0 means success and the file is shown in its folder; anything else shows the last 200 characters of ffmpeg's error output.

// line 5311: PSD (Photoshop) run-length packing
// "PackBits": a run of equal bytes becomes
// [count, byte]; anything else is copied
function psdPack(src, o, n, out) {
  let i = 0;
  while (i < n) {
    let j = i;
    while (j < n - 1 && j - i < 127
           && src[o + j] == src[o + j + 1]) j++;
    if (j > i) {                 // a repeat
      out.push(-(j - i) & 255, src[o + i]);
      i = j + 1; continue;
    }
    // … otherwise copy literal bytes
  }
}

  2. It uses the two fonts every PDF reader has built in (Helvetica and Helvetica-Bold), so no font files have to be embedded, and the canvas goes in as a JPEG at 92% quality.
  3. PSD layers: the export re-draws the frame once per layer (background, grid, pattern, labels, data, power…) using the same render() with a flag (LY('pat'), LY('lab')…) that skips everything except that layer. Each layer is packed with PackBits, a simple compression Photoshop understands.

var Filesystem = reg('Filesystem'),
    Share = reg('Share'), KeepAwake = reg('KeepAwake');
var CHUNK = 3 * 1024 * 1024;   // 3 MB pieces
async function write(path, blob) {
  for (var i = 0; i < blob.size; i += CHUNK) {
    var data = await b64(blob.slice(i, i + CHUNK));
    await Filesystem.appendFile({path, data});
  }
}

  1. Capacitor wraps a web page in a native Android or iOS app and offers "plugins" for phone features. The bridge registers the ones TileSmith needs and exposes them as window.TSM.
  2. The app checks MOBILE (Capacitor present and TSM loaded). Where the desktop would write with fs, it calls the bridge instead.
  3. Chunks: phone plugins pass data as base64 text. Converting a 200 MB recording in one go would run a phone out of memory, so the bridge writes it 3 MB at a time.
Part 23 · Tests and releases

Robots click every button

What it does

Every change gets test builds for every platform. A release is one button on GitHub: it builds all the installers, then the manuals (with fresh screenshots), then scans every file on VirusTotal.

Sysadmin translation

A CI pipeline. Three GitHub Actions workflows chained together, each starting only when the one before succeeds, like Ansible handlers.

How the code works
release.yml · Build and releaseelectron-builder makes .exe, .dmg, .pkg, AppImage, .deb, .rpm, .pacman, Snap and Flatpak; Gradle makes the Android .apk. Runs on every pull request too, as a test build.
when a release is published
docs.yml · Build documentationPython + Playwright open the real app in a headless browser, click through it, take and annotate screenshots, and write the PDF manuals and the app spec.
then
virustotal.yml · VirusTotal scanuploads every file and commits the results to VIRUSTOTAL.md

  1. Why test through the browser? The app has no separate "engine" to test on its own. Everything lives in the page, so the tests drive the page like a user would, with Playwright, a library that remote-controls a browser.
  2. The manuals are code too: make_manual.py builds the PDF from the live app, and annotate.py draws the red circles and arrows on the screenshots. When the UI changes, the next release's manual changes with it.
  3. Unsigned builds: signing certificates cost money every year, so Windows and macOS warn on first run. Publishing the VirusTotal results next to the source is the trade-off for that.
