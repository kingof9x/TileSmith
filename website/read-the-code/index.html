Reading the TileSmith code

The How TileSmith works tour explains what each part of the app does and how. This guide is the other half: how to find your own way around the code, so you can answer your own questions about it. It's written for people who live in terminals and config files, not for developers.

1 filetilesmith-desktop/app/index.html is the whole app
~6,400lines, some of them 100,000+ characters long
~440functions, in about 50 labelled sections

Scroll, or use ← → to jump between sections. Line numbers are from the current version on GitHub and are refreshed by manual-src/make_code_guides.py.

1 · The folders

Most of the repo isn't the app

Clone the repository and you'll find about 400 files. Almost all of them are packaging, tests and documentation. The app itself is one HTML file. Read that first, and come back to the rest when you have a question it doesn't answer.

Sysadmin translation

Think of a server's /etc: hundreds of files, but on any given day you only care about the one config for the service you're working on. The rest is support.

2 · The map

A map of index.html

The file reads top to bottom like a show file: looks first (CSS), then the empty stage (HTML), then two scripts. The first script is the translation table. The second is the app, in about 50 sections, each starting with a // ---------- header comment that says what's in it.

Start here

At the top of the second script is a 50-line comment called HOW THIS FILE WORKS. It's the author's own map of the code, in plain English. Read it before anything else, then use the map below to jump to a section.

3 · Tools

Your editor and grep do most of the work

You don't need an IDE. Any editor that can jump to a line and list functions will do. VS Code is free and handles this file well. And a terminal with grep is often faster than either.

Sysadmin translation

Reading code is log analysis. You don't read a 6,400-line log from the top: you grep for the thing you care about, look at the lines around it, and follow the trail.

In VS Code

Ctrl+GGo to a line number (Mac: ⌃+G)
Ctrl+Shift+OList every function in the file; type to filter
F12Jump to where the name under the cursor is defined
Shift+F12List every place that uses it
Alt+←Jump back to where you were
Ctrl+Shift+FSearch every file in the folder
Alt+ZWord wrap on or off. Many lines hold several statements, so wrap helps, but turn it off near line 67 (the fonts).

In a terminal

The one habit that matters: pipe grep into cut. Some lines are 100,000+ characters, and one match on those can flood your terminal.

# every section header, with its line number
grep -n '^// ----------' index.html | cut -c1-120

# where is a function defined?
grep -n '^function render(' index.html | cut -c1-120

# every place a setting is used, with 60 characters either side
grep -n -o -E '.{0,60}S\.derate.{0,60}' index.html

Run these from tilesmith-desktop/app/. -o prints only the match, so .{0,60} on both sides gives you a window of context even on a giant line.

4 · Short names

Decoding the one-letter names

The code uses short names for the things it touches most, the way you'd alias ll or k for kubectl. Once you know the dozen big ones, most lines read fine. Type in the box to filter.

Pattern to spot

Features share a prefix: gl… is tile faults (glitches), sh… is sharing (Spout and Syphon), rc… receiving cards, ds… distros, z… locations (they were once called zones), un… undo, upd… updates, rec… video recording, cv… canvases.

5 · Follow a setting

From a tick box to the maths

The best way to learn a codebase is to pick one thing you understand from the outside and follow it all the way in. Here's Load circuits to 80%, the continuous-load rule, from its default value to the number in the Engineering panel. Step through it, then try the same with a setting you care about.

Sysadmin translation

It's tracing a config key: where's the default, which daemon reads it, what does it change? Every setting in TileSmith follows these same six stops.

Every setting starts life as one line in S, near the top of the second script. The key is derate and it's on by default. The header comment above S says what makes a key special: it's saved, undone and restored automatically.

Search for derate: to find it. In the spec, the same key has a row in the settings table (part 8).

The left panel isn't written in HTML by hand. build() generates it, and F() makes one labelled box. Its first argument is the key in S; the type 'check' makes a tick box.

So the tick box comes out as <input type="checkbox" data-k="derate">. That data-k attribute is the whole link between the box and the setting.

There's no code attached to that one box. Instead, a single listener on the whole page hears every edit, in any box, and hands it to applyKey(), then calls sync().

The lines in between handle special boxes first, each ending in return. Ordinary boxes like this one fall through to the last line. HEAVY lists number boxes (like columns and rows) that wait until you finish typing.

applyKey() reads the key from data-k, gets the value the right way for the kind of box (a tick box gives true or false), clamps numbers to LIM, and writes it into S.

S[k]=v is the moment the setting changes: S['derate']=false. Everything after it on that line is special cases for other keys.

Saving isn't wired to each box either. Every input, change, click or drag anywhere on the page calls saveSoon(), which waits 0.4 s and then writes everything.

clearTimeout then setTimeout is a debounce: ten clicks in a row cause one write, 0.4 s after the last.

Finally, the power code reads the setting. pwC() works out one circuit for a wall. The last part of the line is the formula from the spec: usable watts = volts × amps × 0.8 (if derated) × power factor.

S.derate?.8:1 reads "if derate is on, 0.8, otherwise 1". At 120 V and 20 A that's 1,920 W per circuit, so a 120 W tile fits 16 to a circuit. Grep for S.derate and you'll find the other places that read it: the distro legs, the notes and the PDF spec sheet.

6 · Follow a button

From a button to its code

Buttons work like settings: no code is attached to each one. A button has a data-a (action) attribute, and one click listener looks the action up in a list. To find what Export PDF does, search for its label, read its action name, then search for that.

Sysadmin translation

It's a dispatch table, like a case "$1" in start) … ;; stop) … ;; esac block in an init script. The button's action name is $1.

  1. Find the label. grep -n -o -E ".{0,40}'Export PDF'.{0,20}" index.html finds where the top bar is built. B() makes a button whose action is its first argument, 'pdf'.
  2. Find the dispatcher. One click listener reads data-a and calls the function with that name from a long list of short handlers.
  3. Find the handler. Search for pdf(){. The handler is one call, so the real work is in exportPDF(), and the binder is the same function with one switch flipped.
  4. Read the function. grep -n '^function exportPDF' index.html takes you to it, under its section header in the map (part 2).
7 · Live

Read it while it runs

You can talk to the running app. Open tilesmith-desktop/app/index.html straight from disk in Chrome or Edge, press F12 and pick Console. Every name from part 4 is right there. Type one and press Enter.

Sysadmin translation

It's attaching a shell to a running container. Look at the state, change a value, call a function, and watch what happens. Close the tab and nothing you did is kept, unless the app autosaves it, so use a fresh browser profile if you care about your settings.

// look at the state
S.cols
S.preset
walls.length

// change it, then tell the panels
S.cols = 12; storeWall(); sync()

// call the maths directly
pwC(S)
wst(walls[cur])
// list every setting and its value
console.table(S)

// time one frame of drawing
console.time('render'); render(); console.timeEnd('render')

// see a function's code without searching
render.toString().slice(0, 400)

This is exactly how the tests work: they open the page in a headless Chrome and type lines like these (part 9). Changing S.cols without storeWall() works for a moment, until something reloads the wall from its saved copy. That's the S/walls mirror from part 4 in action.

8 · The spec

The spec is the manual for the code

TileSmith-App-Spec.md describes every feature in plain English, and its settings table uses the same keys as S. When code looks odd, look its key up in the spec: it usually says what the code is aiming for, with the formula.

Sysadmin translation

It's the man page. The code is the binary; the spec is what it's documented to do. When they disagree, that's a bug in one or the other, and worth reporting.

Search the spec for a setting's key in backticks (`derate`) to land on its row. The formulas for data and power are in the Data wiring and Power sections, with worked examples.

9 · Tests

Tests tell you what's meant to happen

Each file in manual-src/tests/ opens the real app in a headless Chrome, sets things up through the console, and checks the result. They're short, and they're the most precise statement of what a feature should do. Here's a whole one: it checks that the power wiring patterns go the right way.

Sysadmin translation

They're health checks: put the service in a known state, poke it, and assert the answer. assert is test … || exit 1.

  1. Line 8 opens the app from disk and clears its saved settings, so every run starts the same.
  2. Line 9 is console code like part 7: an 8 × 6 wall, a distro, power shown, Snake wiring.
  3. Lines 10 to 15 click each of the 8 wiring-pattern buttons and check that the first circuit runs along columns for vertical patterns and along rows for horizontal ones.
# one-time setup (Python 3 and Node.js already installed)
pip install playwright pillow pypdf
python3 -m playwright install chromium

# run one test, then all of them
python3 manual-src/tests/wpat_test.py
python3 manual-src/tests/run_all.py
10 · History

Ask git why

The code says what happens. The history says why. Every change came through a pull request on GitHub with a description, so when a line puzzles you, find the change that added it.

Sysadmin translation

It's the change log for a config managed in git. git log -S answers "when did this value first appear?", like grepping old backups.

# every commit that added or removed the text "S.derate"
git log -S 'S.derate' --oneline -- tilesmith-desktop/app/index.html

# who last changed the first two lines of pwC(), and in which commit
git blame -L '/^function pwC(/,+2' tilesmith-desktop/app/index.html | cut -c1-80

# one commit's description and files
git show --stat <commit>

Commit titles end with the pull request number, like (#57). Open github.com/kingof9x/TileSmith/pull/57 for the full story, with screenshots and the discussion. On GitHub itself, the Blame button on any file does the same as git blame.
